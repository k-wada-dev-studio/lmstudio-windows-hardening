# Live test report — 2026-08-20

## Result

Partial pass. LM Studio successfully recognized, estimated, loaded, inferred with,
and unloaded the real model. The product scripts are **not yet live-test approved**
because their headless preflight dependency did not start and no real shared-folder
model source was connected.

## Environment observed

- Windows desktop installation of LM Studio
- `lms` CLI commit `71bd99c`
- one local LLM: `openai/gpt-oss-20b`
- GGUF variant: MXFP4
- selected runtime: `llama.cpp-win-x86_64-nvidia-cuda12-avx2@2.28.2`
- configured context length used for the test: 8192

## Passed live checks

- LM Studio GUI reached CLI status `running` in approximately four seconds
- `lms ls --json` returned one LLM and one embedding model
- `lms runtime ls` returned the installed GGUF runtimes
- `lms load --estimate-only openai/gpt-oss-20b -y` succeeded
- estimated GPU and total memory were both 11.28 GiB
- the model loaded with identifier `approved-model`
- `lms ps --json` reported exactly one idle model with context length 8192
- a short local inference returned successfully
- `lms unload --all` succeeded and the final loaded-model list was empty

## Failed or blocked checks

- `lms daemon up --json` remained at `Waking up LM Studio service...` and did
  not produce a running daemon
- removing a confirmed stale PID lock did not change that result
- the current Setup and secure-launch scripts therefore fail closed during their
  headless preflight on this machine
- no connected UNC share or mapped shared drive containing a GGUF was available
- `config/deployment.local.psd1` was intentionally not fabricated without a real
  deployment path
- shared-folder symbolic-link registration, SMB access after Firewall enforcement,
  full Setup execution, secure-launch execution, and Restore execution remain untested

## Machine state after the test

- loaded model count: zero
- LM Studio-related process count: zero
- managed Firewall rule count: zero
- `%USERPROFILE%\.lmstudio\secure-setup` was not created
- the project did not harden `settings.json` or change `mcp.json`

The GUI was launched through the elevated test runner because desktop process
creation required approval in this environment. It was model-empty when stopped.
This does not validate the product launcher's requirement to run LM Studio as a
normal user.

## Required before release

2. Supply the real shared-folder GGUF path in the gitignored deployment configuration.
3. Re-run Setup, secure launch, inference, network-boundary checks, and Restore on
   a disposable or explicitly approved Windows profile.
4. Confirm the GUI is launched as the normal LM Studio user in that test.

## Post-test code change

After this report exposed the blocker, schema version 4 removed the headless
daemon dependency. Setup now records a pending model-validation state after link,
Firewall, and JSON preparation. The first secure launch starts the normal-user
GUI, resolves the setup-managed repository, verifies runtime and memory estimate,
loads the model, and only then commits the model and runtime identities. This
change has static and simulated coverage but has not yet completed the live
shared-folder retest described above.

## Vision-package change

Schema version 5 adds optional split-GGUF vision support: one primary GGUF plus
one matching `mmproj-*.gguf`. Static and simulated behavior tests cover package
detection, state handling, capability checks, and restore handling. The current
test share contains only the primary GGUF, so a real image upload remains
untested until the matching projector is placed on the share and Setup and the
secure launcher are run again.
